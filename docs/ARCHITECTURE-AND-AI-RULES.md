# 아키텍처·AI 협업 규칙 (필수)

이 문서는 **NullReferMusic** 프로젝트에서 사람(기획/개발)과 AI 코딩 어시스턴트가 함께 일할 때 **반드시 지켜야 하는** 규칙이다.  
웹·모바일 앱 **모두**에 적용된다.

---

## 1. 일상적인 코딩 지시

사용자가 **구체적인 구현·수정·버그 수정** 등을 지시한 경우:

- 명세가 분명하면 **바로 구현**한다.
- 별도의 아키텍처 승인 절차는 필요 없다.

### ⚠️ APK/IPA 빌드 금지 규칙

**기능을 새로 만들거나 수정하는 작업에서 사용자가 "APK를 말아줘 / APK 빌드 / APK 생성"을 명시적으로 요청하기 전까지는 APK(또는 IPA)를 빌드하지 않는다.**

- 코드·기능 변경만 하고, 빌드는 대기한다.
- `npx tsc --noEmit` 타입 검증은 실행해도 된다.
- 사용자가 APK를 요청하면 `docs/RELEASE-APK-IPA-RULE.md` 절차를 따른다.

---

## 2. 아키텍처·구조 결정이 필요한 경우 (사전 확인 필수)

다음에 해당하면 **코드 작성·큰 폴더 구조 변경 전에 반드시 사용자에게 확인**을 받는다.

- 기술 스택 선택·변경 (프레임워크, 주요 라이브러리, 빌드 체인 등)
- **웹**과 **모바일 앱**의 역할 분리, API 설계, 인증·동기화 방식
- 모노레포/멀티레포, 배포·환경 구성의 큰 틀
- 데이터 모델·저장소 전략이 제품 전체에 미치는 설계
- 사용자에게 장기적으로 구속되는 폴더·모듈 경계

**확인 없이 임의로 “전체 구조를 정해서” 진행하지 않는다.**

---

## 3. 확인을 받을 때 제공할 내용

아키텍처 관련 제안을 할 때는 사용자에게 **다음을 설명**한다.

1. **제안하는 구조의 개요** (구성 요소가 무엇이고 어떻게 연결되는지)
2. **그렇게 선택한 이유** (단순함, 유지보수, 보안, 팀 역량, 생태계 등)
3. **대안**이 있다면 간단한 비교와 **트레이드오프**
4. **사용자가 결정해야 할 질문** (명확한 선택지가 있으면 나열)

설명은 대화로 전달하고, 합의된 내용은 필요 시 별도 설계 문서나 이 저장소의 `docs/`에 반영한다.

---

## 4. 문서 유지

- 이 파일(`docs/ARCHITECTURE-AND-AI-RULES.md`)은 **필수 규칙**으로 둔다.
- 아키텍처 합의가 바뀌면 **관련 설계 문서와 함께** 이 규칙이 여전히 유효한지 점검한다.
- AI 어시스턴트는 작업 시 이 문서를 **우선 준수**한다.
- **APK·IPA 등 최종 설치 빌드**와 개발(Expo Go) 간 기능 동등성·검증 절차는 **`docs/RELEASE-APK-IPA-RULE.md`** 를 따른다. 해당 문서는 **동등하게 필수**다.

---

## 5. 제품 UI 카피·온스크린 설명

- 앱·웹 **제품 화면**에는 사용법 안내, 도움말 문단, 장식용 설명 텍스트를 넣지 않는다.
- 컨트롤 주변의 **긴 설명**, 문장형 `accessibilityLabel`·UI 전용 주석도 두지 않는다. (접근성이 필요하면 짧은 역할명만.)
- 버튼·스위치 레이블은 **짧은 명사·동사**로 역할만 드러낸다.
- 운용·설치·네트워크 안내는 **`docs/`** 등 개발 문서에만 둔다.

---

## 6. 웹·앱 UI 시각 통일

- **Expo(웹·iOS·Android)는 하나의 제품 UI**로 본다. 같은 화면은 **테두리 색·두께, 배경, 그림자(또는 elevation), 간격, 반경**이 플랫폼 간에 어긋나지 않게 맞춘다.
- 웹 전용 `boxShadow` 한 겹, 앱 전용 `elevation`만 다른 식으로 **한쪽만 빨간 테두리·한쪽만 무테**가 되지 않게 한다. 공통 값은 **`nrmTokens` / `nrmShadow` 등 토큰**으로 빼고, `.web.tsx`는 **임베드 기술(iframe) 한정**으로만 둔다.
- 새 카드·패널·모달을 만들 때도 위 원칙을 적용하고, 변경 후 **웹과 네이티브 둘 다**에서 한 번씩 확인한다.
- 같은 기능의 **placeholder·알림 문구 문자열** 등은 웹 전용/앱 전용으로 갈라 쓰지 않고, **`app/lib/` 등 한곳에 상수로 두고** 동일 문자열을 쓴다.
- **메인 페이지(검색창 위) 로고는 `CI 마크 + nullreference music` 단일 워드마크**로 고정하고, 웹·모바일 모두 같은 컴포넌트(`NrmLogo`)를 재사용한다.
- 로고 텍스트·아이콘 색은 **배경과 대비가 충분히 보이는 값**으로만 쓴다. (라이트 배경에서 흰색 본문 금지) 로고 색 변경 시 라이트/다크를 모두 확인 후 반영한다.

---

## 7. 알림·오류 표시 (인라인 금지)

- 검색창·카드 **내부**에 오류/실패 문구를 **붙여 두지 않는다.** “나중에 에러 띄울 자리”로 **빈 여백·고정 슬롯**도 만들지 않는다.
- API 실패, 검증 오류, 네트워크 문제 등 사용자에게 알릴 일은 **본문 레이아웃과 분리**하고, **웹·iOS·Android 모두 동일한 오버레이 모달**로 처리한다. (`window.alert`·시스템 `Alert`로 제각각 두지 않는다.)
- 호출부는 **`notifyUser(메시지)`** (`app/lib/nrmUserNotify.ts`) 한 곳으로만 보내고, 실제 UI는 루트의 **`NrmNotifyHost`** (`app/components/nrm/NrmNotifyHost.tsx`)가 띄운다.
- **브랜드 타이틀(알림 헤더)**  
  - 문구는 **`NullRefer` + 그라데이션 캡슐 안의 `Music`** (이탤릭·넓은 자간)으로 통일한다.  
  - 카드는 **큰 라운드(약 28px)·얇은 테두리·부드러운 그림자**, 본문은 짧은 문단 톤, 하단 버튼은 **가로 그라데이션 캡슐**과 캐주얼한 확인 카피(예: 알겠어요)로 **MZ 톤**을 맞춘다.  
  - 라이트/다크는 `useColorScheme`에 맞춰 카드 배경·글자색만 조정하고, 위 톤은 유지한다.

## 8. 요약

| 상황 | 행동 |
|------|------|
| 구체적 구현 지시 | 바로 진행 |
| 웹/앱 전반 구조·스택·API 등 큰 설계 | **사용자 확인 후** 진행 |
| 설계 제안 시 | 구조 요약 + 이유 + (가능하면) 대안 |
| 제품 UI | §5 준수 — 설명성 카피·온스크린 주석 금지 |
| 웹·앱 동일 화면 | §6 준수 — 시각 스펙·토큰 통일 + 메인 로고 대비 검증 |
| 오류·알림 | §7 준수 — 인라인 금지·`notifyUser` + `NrmNotifyHost` 모달·브랜드 MZ 톤 |
| **APK·IPA·릴리스 빌드** | **`docs/RELEASE-APK-IPA-RULE.md` 필수** — Expo Go만으로 충분하다고 가정하지 않음 |

## 9. 사용자 메시지 비기술 원칙 (매우 중요)

- 사용자에게 직접 보이는 메시지에는 개발 용어(스택, 모듈명, errno, HTTP 코드, Exception 등)를 넣지 않는다.
- 사용자 메시지는 짧고 직관적으로 "무엇이 안 됐는지"만 전달한다.
- 원인을 간단히 특정할 수 없는 경우에는 반드시 아래 문구로 통일한다.
  - `알 수 없는 오류가 발생했습니다.`
- 상세 원인·코드·컨텍스트는 사용자 메시지가 아니라 개발 로그(`logNrmRunError`)에만 남긴다.
