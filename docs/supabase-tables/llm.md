# LLM 관련 테이블

원격 Supabase에 이미 생성된 스키마다. (PascalCase 식별자, quoted `"TableName"`)

## 스키마 정규화 (2026-07-22, `20260722160000_llm_provider_model_normalize.sql`)

이전에는 `LLMProvider` 한 테이블에 **모델마다 행**이 있고 모든 행이 같은 `ApiKey`를 복제하고 있었다.
정규화 후:

```
LLMProvider (1) ──< LLMModel (N)           제공자 1개(예: Google)가 여러 모델 보유, ApiKey는 제공자에만
                ├──< LLMUserPermission (N)  사용자×제공자 승인·할당 (모델 단위 아님)
                ├──< LLMUserQuota (N)       사용자×제공자×월 누적
                ├──< LLMUserMonthlyAllocation (N)  월별 할당 이력(조회용)
                ├──< LLMTokenHistory (N)    ProviderID + ModelID
                └──< ChatSession (N)        ProviderID + ModelID → ChatMessage
```

| 테이블 | 역할 |
|--------|------|
| **LLMProvider** | 제공자(ApiKey 소유자). 컬럼: `ProviderID`, `ProviderName`, `ApiKey`, `RegDate` 만. 시드: `ProviderID=1`, `ProviderName=Google` |
| **LLMModel** | 개별 모델(구 LLMProvider rename). PK=`ModelID`. `ProviderID` FK. **ApiKey/DailyLimit/MonthlyLimit/ProviderName 없음** |
| **LLMUserPermission** | 사용자×**제공자** 승인·할당 |
| **LLMUserQuota** | 사용자×**제공자**×월 누적. 정규화 시 모델별 행을 SUM으로 합침 → 제공자 1개면 `(SerialNo,TargetMonth)` 사실상 유일 |
| **LLMTokenHistory** | 호출 이력. `ProviderID`(제공자) + `ModelID`(실제 모델) |
| **ChatSession** | `ProviderID` + `ModelID` — 세션 생성 시 모델 고정, 이후 요청도 그 모델 사용 |

채팅 요청 body는 `modelId`(클라이언트가 고른 모델). Edge Function/`nrm_rpc_chat_prepare_turn`이 `LLMModel`→`LLMProvider` join으로 ApiKey를 얻고, 권한/쿼터는 **provider** 단위로 체크한다.

`SerialNo`는 사용자 일련번호다. `LLMUserQuota`·`LLMTokenHistory`·`LLMUserPermission`의 `SerialNo`는 **varchar**로, 앱 `getNrmAppSerialNo()` 원문을 그대로 저장한다.

## LLMProvider

LLM 제공자(ApiKey 소유자). 정규화 후 **모델 목록이 아니다**.

| 컬럼 | 타입 | 기본값 | NULL | 설명 |
|------|------|--------|------|------|
| `ProviderID` | `bigint` IDENTITY PK | — | NO | LLM 제공자 고유번호 |
| `ProviderName` | `varchar` | — | NO | 제공자명 (예: `Google`) |
| `ApiKey` | `text` | — | NO | LLM API Key (이 제공자의 전체 모델이 공유) |
| `RegDate` | `timestamptz` | `now()` | NO | 등록일시 |

RLS: SELECT만 anon/authenticated. `ApiKey`는 컬럼 단위 REVOKE — 앱 `select`로는 못 읽고 Edge Function(service_role)만 읽는다.

### DDL

```sql
CREATE TABLE public."LLMProvider"
(
    "ProviderID"    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "ProviderName"  varchar NOT NULL,
    "ApiKey"        text NOT NULL,
    "RegDate"       timestamptz NOT NULL DEFAULT now()
);
```

## 보안 — RLS·컬럼 권한 (`20260721120000_llm_chat_security_harden.sql`)

이 6개 테이블은 생성 시 RLS를 켜지 않아 "쓰기는 RPC로만"이라는 원칙이 적용되지 않고 있었다. 아래로 강화:

- `LLMProvider`/`LLMUserPermission`/`LLMUserQuota`/`LLMTokenHistory`/`ChatSession`/`ChatMessage` 모두 `ENABLE ROW LEVEL SECURITY` + `SELECT` 정책만 anon/authenticated에 허용(`USING (true)`). **쓰기 정책은 없음** → 모든 쓰기는 `nrm_rpc_*` (SECURITY DEFINER) 경유.
- `LLMProvider."ApiKey"`는 RLS(row 단위)로 못 숨기므로 **컬럼 단위**로 `REVOKE SELECT ... FROM anon, authenticated` 후 나머지 컬럼만 `GRANT SELECT (...)`. 앱이 실수로 `select=*`를 하더라도 DB가 `ApiKey`를 막는다.

## AI Lab 채팅 전송 — Edge Function + RPC (실제 구현)

`ApiKey`는 클라이언트(APK)에 절대 내려주지 않는다. 실제 LLM 호출은 Edge Function
`supabase/functions/llm-chat-send`(service_role)에서만 수행:

1. **`nrm_rpc_chat_prepare_turn`** (service_role 전용, `20260721130000_chat_send_rpc.sql` → 한도 체크 필드 추가는 `20260721140000_chat_provider_limit_check.sql`) — DB 왕복 1회로:
   세션 확보/생성 → 사용자 메시지 저장 → `LLMProvider`(ApiKey 포함, `DailyLimit`/`MonthlyLimit`과 그 기준 **전체 사용자 합산** 현재 사용량 `providerDailyUsed`/`providerMonthlyUsed`도 함께)·`LLMUserPermission`·해당월 `LLMUserQuota`·최근 대화이력(최대 40건, `system` 제외)을 한 번에 조회해 반환.
   - `providerDailyUsed` = 오늘(UTC) `LLMTokenHistory."TotalToken"` 합계(해당 `ProviderID`, 전체 사용자). `DailyLimit=0`이면 이 집계 자체를 건너뛴다(가장 흔한 "무제한" 케이스에서 추가 비용 없음).
   - `providerMonthlyUsed` = 이번 달 `LLMUserQuota."TotalToken"` 합계(해당 `ProviderID`, 전체 사용자). `MonthlyLimit=0`이면 건너뛴다.
2. Edge Function이 위 결과로 **① 제공자(모델) 단위 `DailyLimit`/`MonthlyLimit`** → **② 사용자 권한(`IsApproved`)** → **③ 사용자 개인 쿼터(`AllocatedToken`)** 순으로 선체크 후, 모두 통과하면 프로바이더 어댑터(`ProviderName` 기준, 지금은 `Gemini`만 구현)로 실제 LLM API를 호출. Gemini `generateContent` 응답의 `usageMetadata`(`promptTokenCount`/`candidatesTokenCount`/`totalTokenCount`)를 그대로 써서 **토큰 집계용 별도 API 호출이 필요 없다.**
3. **`nrm_rpc_chat_finalize_turn`** (service_role 전용) — DB 왕복 1회로: 응답(`assistant`/`system`) 메시지 저장 + `ChatSession.UpdateDate` 갱신 + (실제로 AI 요청을 시도한 경우만) `LLMTokenHistory` 기록.
4. **`nrm_rpc_increment_llm_user_quota`** (service_role 전용) — `LLMUserQuota` 누적 upsert(`ON CONFLICT` 원자적 증가). 사용자 응답을 이미 반환한 **뒤** `EdgeRuntime.waitUntil()`로 백그라운드 실행 — 응답 지연에 전혀 영향 없음.

사전 체크 실패(제공자 한도 소진/권한 없음/쿼터 초과)는 AI 요청 자체를 하지 않으므로 `LLMTokenHistory`에 기록하지 않는다(요구사항). 네트워크 오류·프로바이더 오류처럼 **AI 요청을 시도한** 경우는 실패해도 `isSuccess=false`로 기록한다.

**컬럼명 정정 (2026-07-22)**: 최초 추가(`20260721150000`) 시 `isSucess`(오타)로 만들어졌던 것을 `20260722100000_llm_token_history_is_success_rename.sql`에서 `RENAME COLUMN`으로 `isSuccess`로 정정했다(데이터 보존). `nrm_rpc_chat_finalize_turn`도 같은 마이그레이션에서 `isSuccess` 컬럼을 쓰도록 `CREATE OR REPLACE`. 과거 마이그레이션 파일(`20260721130000`/`20260721140000`/`20260721150000`) 자체는 이미 원격에 적용된 이력이라 수정하지 않고 그대로 둔다(신규 마이그레이션으로만 교정 — 이 저장소 관례).

**"토큰이 만료되었을 경우" 메시지의 의미 구분** (설계 결정, 2026-07-21):
- 개인 할당량(`LLMUserPermission.AllocatedToken`) 소진 → `토큰이 만료되었어요. 관리자에게 문의해주세요.` (관리자가 늘려주면 바로 해결됨)
- 모델(`LLMProvider`) 자체의 `DailyLimit`/`MonthlyLimit`(전체 사용자 합산) 소진 → `지금 이 모델을 많은 사용자가 이용하고 있어 잠시 이용이 어려워요. 나중에 다시 시도해 주세요.` (관리자 문의로 즉시 해결되는 성격이 아니므로 문구를 구분)
- Gemini API 자체의 인증 오류(401/403) → `네트워크 문제로 요청할 수 없어요...` (앱에 실사용자 로그인 토큰이 없어 "토큰"이라는 표현은 위 두 가지 앱 내부 토큰 할당량 개념에만 사용)

멀티 프로바이더 확장: Edge Function 안 `ADAPTERS: Record<ProviderName, LlmAdapter>` 맵에 새 어댑터(예: OpenAI)를 추가하고 `LLMProvider.ProviderName`을 맞추면 나머지 로직(권한/쿼터/기록/세션)은 그대로 재사용된다.

### 스트리밍 응답(타이핑 효과) — NDJSON (2026-07-22)

사전 체크(제공자 한도/권한/쿼터)를 통과하면 Edge Function은 Gemini를 호출해 응답을 받는다(업스트림 호출 방식은 아래 "후속 수정 2" 참고 — 2026-07-22부터 논스트리밍 `generateContent` + 서버 재생으로 바뀌었다). Edge Function → 클라이언트 구간은 이 업스트림 방식과 무관하게 항상 "타이핑 효과"용 **NDJSON**(줄바꿈으로 구분된 JSON) 스트림이다(`Content-Type: application/x-ndjson`):

| `type` | 시점 | 내용 |
| --- | --- | --- |
| `meta` | `prepare_turn` 완료 즉시(권한/한도 체크 **전**) | `sessionId`/`isNewSession`/`title`(임시)/`userMessage` — 클라이언트가 사용자 메시지·세션을 바로 확정 표시 |
| `delta` | LLM 스트리밍 중 0회 이상 | `text`(조각) — 어시스턴트 말풍선에 이어붙여 타이핑 효과 |
| `final` | 이번 턴 확정 메시지 저장 완료 후 1회, 스트림 종료 | `message`(assistant 또는 system 최종 `ChatMessage` row) — `delta`로 이미 보여준 텍스트와 항상 일치 |
| `error` | 복구 불가 오류(예: finalize 저장 실패) | `message` — 이 경우 `final` 없이 스트림이 끝날 수 있음 |

사전 체크 실패·`adapter_missing`처럼 LLM을 호출하지 않는 경로도 **동일한 스트림 프로토콜**을 쓴다(다만 `delta` 없이 곧바로 `final`). `prepare_turn` 자체가 실패한 경우(파라미터 오류 등, 세션도 아직 없음)만 스트리밍 없이 평범한 JSON 에러 응답을 즉시 반환한다.

클라이언트(`app/lib/nrmLlmChatSend.ts`)는 `@supabase/supabase-js`의 `functions.invoke()`(RN 기본 fetch가 응답을 통째로 버퍼링해 스트리밍이 안 됨) 대신 **`expo/fetch`**(Expo SDK 50+ 네이티브 스트리밍 fetch, `response.body`가 진짜 `ReadableStream`)로 Edge Function URL(`getNrmSupabaseFunctionUrl()`)을 직접 호출한다. Authorization/apikey 헤더는 publishable key를 그대로 사용(`functions.invoke()`와 동일한 인증 방식).

클라이언트 화면(`NrmDiscoverAiLabScreen.tsx`)은 전송 즉시(첫 `delta` 도착 전) "타이핑 중" 점 3개 애니메이션이 있는 빈 어시스턴트 버블을 먼저 붙인다(`NrmAiLabMessage.typing`, `NrmAiLabTypingDots.tsx`). Gemini의 내부 추론(thinking, 아래 참고)이 몇 초씩 걸릴 수 있어, 아무 반응 없이 멈춘 것처럼 보이지 않게 하기 위함이다.

사용자가 좌측 메뉴에서 직접 고른 모델(`LLMProvider.ProviderID`)은 `app/lib/nrmAiLabModelPreference.ts`가 `AsyncStorage`(기기 로컬, 서버 저장 아님)에 저장한다(2026-07-22) — 저장 전에는 AI Lab을 나갔다 들어올 때마다 모델 선택 컴포넌트(`NrmAiLabModelPicker.tsx`)가 매번 기본 모델(`pickDefaultLlmProviderId`)로 되돌아가는 문제가 있었다. 과거 대화를 열면(`handleSelect`) 그 세션이 생성됐을 때의 모델로만 일시적으로 바뀌고 이 저장값은 덮어쓰지 않는다.

#### 알려진 이슈 — Gemini "thinking"이 강제인 모델의 지연·잘림 (2026-07-22)

`gemini-flash-latest`(2026-07-22 기준 `gemini-3.5-flash`로 alias, `docs` 위 문단 참고)로 실제 로그(`llm_call_ok`)를 확인한 결과:

- 매 요청마다 `usageMetadata.thoughtsTokenCount`가 ~1,100~1,200 정도 소모되고, 그 뒤 시각적으로 보이는 답변은 극히 짧게(문장 중간에서도) 끝난 채 스트림이 종료된다. `candidates[0].finishReason`이 **한 번도 오지 않음**(로그에 `finishReason` 필드 자체가 없음) — 모델이 스스로 끝낸 게 아니라 연결이 외부에서 끊긴 것으로 보인다.
- `generationConfig.thinkingConfig.thinkingBudget`를 `0`으로 주면 이 모델은 **400 Invalid Argument**로 거부한다. `4096`으로 줘도(값 자체는 받아들여지는 것으로 보임) 총 사용 토큰·지연·잘림 패턴이 동일했다 — thinking 예산을 우리가 조절해서 고칠 수 있는 문제가 아니었다.
- `generationConfig.maxOutputTokens`를 넉넉히(`8192`, `GEMINI_CHAT_MAX_OUTPUT_TOKENS`) 올려도 총 사용 토큰이 그 한도에 한참 못 미치는 상태(~1,150~1,240)에서 끊겨, 우리 쪽 토큰 상한이 원인이 아님을 확인했다.
- 결론: 이 특정 alias(당시 최신 preview일 가능성이 높은 모델)의 서버 쪽 지연/자원 제약으로 보이며, 코드로 해결 불가능. **더 빠르고 완전한 답변이 필요하면 `IsActive`를 thinking이 없는 안정 모델(예: `models/gemini-2.0-flash`) 또는 확실히 지원되는 `models/gemini-2.5-flash` 계열로 옮기는 것을 권장** — `getGeminiThinkingConfig()`가 `2.0` 계열엔 `thinkingConfig`를 아예 안 보내므로 그런 모델은 이 문제와 무관하다.
- 그래도 코드에서 해둔 안전장치: `stream()`/`generateTitle()` 모두 `thinkingConfig`가 400으로 거부되면 그 필드만 빼고 1회 자동 재시도(모델이 바뀌어도 하드코딩 없이 대응). `llm_call_ok` 로그에 `finishReason`/`thoughtsTokens`를 항상 남겨 다음에 같은 증상이 나오면 바로 판단 가능.

#### 후속 수정 1 — maxOutputTokens를 모델별 실제 한도까지 올림 (2026-07-22, 부분적 개선)

`models/gemini-flash-lite-latest`(위 이슈의 alias와 별개로, 실제로 응답이 오는 모델)에서도 "답변이 중간에 잘리고 말이 이상해진다"는 리포트가 있어, 우선 `GEMINI_CHAT_MAX_OUTPUT_TOKENS`(전 모델 공통 `8192`)를 모델 등급별로 올렸다 — Gemini 2.5/3.x(및 `-latest` alias) 계열의 실제 output token 한도는 **65536**(2.0 계열만 8192). `getGeminiMaxOutputTokens(modelName)`가 `getGeminiThinkingConfig()`와 같은 기준으로 `GEMINI_CHAT_MAX_OUTPUT_TOKENS_MODERN=65536`/`..._LEGACY=8192`를 고른다. 답변 품질(자연스러움) 개선을 위해 `generationConfig.temperature=0.8`도 명시(이전엔 모델 기본값 사용).

이 수정 후에도 실제 로그로 재현한 결과 증상이 그대로였다 — 아래 "후속 수정 2"에서 진짜 원인을 확인.

#### 후속 수정 2 — chat도 스트리밍(SSE) 대신 논스트리밍 `generateContent` + 서버 재생으로 전환 (2026-07-22, 근본 수정)

`llm_stream_debug_chunk`/`llm_stream_debug_end` 임시 로그로 `models/gemini-flash-lite-latest` 호출을 직접 재현해 확인한 실제 원인:

- `streamGenerateContent?alt=sse` 응답이 **SSE 프레임 1~2개만 온 뒤 `finishReason` 없이 연결이 그대로 끝났다**(`reader.read()`가 추가 데이터 없이 `done:true`를 반환). `maxOutputTokens`를 65536까지 올려도 무관 — 실제 사용 토큰(`usageMetadata`)이 그 한도에 한참 못 미친 상태(2~13 output tokens)에서 끊겼고, thinking 예산(`thoughtsTokenCount`)도 `0`이었다. 즉 **우리 쪽 토큰 상한·thinking 설정이 원인이 아니라, Google SSE 게이트웨이가 완료 신호(`finishReason`) 없이 스트림을 조기 종료**하는 문제였다(재현율 100%, 메시지 내용과 무관).
- `generateTitle()`은 원래부터 논스트리밍 `generateContent`를 쓰고 있었고 이런 조기 종료 증상이 보고된 적이 없어, **chat(`stream()`) 호출도 동일하게 `generateContent`(논스트리밍)로 교체**했다. 논스트리밍은 응답이 불완전하면 HTTP body/JSON 파싱 자체가 실패하므로(예외 발생) "일부만 온 응답을 완성된 것으로 오인"할 수가 없다 — SSE 프레이밍 특유의 이 취약점을 구조적으로 제거.
- 실시간 네트워크 스트리밍을 포기하는 대신, 응답을 통째로 받아 확정한 뒤 **서버(`emitAsTypingDeltas`)가 `onDelta`를 짧은 간격(16자/30ms)으로 여러 번 호출해 타이핑 효과를 재생**한다. 클라이언트가 받는 NDJSON 프로토콜(`meta`/`delta`/`final`)은 그대로이므로 앱 쪽 코드는 변경 불필요. 실제 네트워크 호출 자체는 1~5초로 이미 빠르고, 전송 즉시 붙는 "타이핑 중" 표시(typing placeholder) 덕분에 체감 차이가 없다.
- 수정 후 실제 테스트(자기소개 5문장/피보나치 함수/전통음식 3가지 소개 등 이전에 2~13 토큰에서 끊겼던 프롬프트들)에서 149~616 output tokens의 완전하고 자연스러운 답변이 생성됨을 확인.
- 위 "알려진 이슈"(`gemini-flash-latest`)의 근본 원인도 이 문서 작성 시점 기준 사실상 동일한 SSE 조기 종료 계열 문제였을 가능성이 높다(다만 그쪽은 thinking 토큰이 커서 시간이 더 걸렸을 뿐) — 이번 수정으로 `stream()`을 쓰는 모든 모델이 함께 개선된다.

### 대화 제목 자동 생성 (2026-07-22)

`nrm_rpc_chat_prepare_turn`은 새 세션 생성 시 여전히 "사용자 메시지를 28자로 자른" **임시 제목**을 즉시 넣는다(세션 INSERT에 `Title NOT NULL`이 필요하고, 응답 속도에 영향을 주면 안 되므로 여기서 LLM을 호출하지 않는다). 이 임시 제목은 `meta` 이벤트로 클라이언트에 먼저 전달되어 좌측 목록에 즉시 표시된다.

실제 "이 대화가 어떤 질문인지"를 요약한 제목은, 새 세션인 경우(`isNewSession`) Edge Function이 사용자에게 스트림을 **다 보낸 뒤** 백그라운드(`EdgeRuntime.waitUntil`)로 Gemini에 짧은 논스트리밍 호출 1회(`generateContent`, 기본 `maxOutputTokens=40`, 사용자 첫 메시지 요약 프롬프트)를 더 보내 생성하고, `nrm_rpc_chat_update_session_title`(service_role 전용)로 `ChatSession.Title`을 덮어쓴다. 응답 지연에는 전혀 영향이 없다(quota 증가와 동일한 "응답 후 백그라운드" 패턴).

- thinking이 강제인 모델(위 "알려진 이슈" 참고)은 추론 토큰이 이 예산을 먼저 소비해버려 제목이 중간에 잘린 이상한 문자열로 나올 수 있었다(실제 사례: `"는데 반"` — 사용자 메시지 중간 단어 파편). 그래서 `getGeminiThinkingConfig()`가 thinking을 끌 수 없는 Pro 계열엔 예산을 `thinkingBudget + 40`으로 넉넉히 늘리고, `stream()`과 동일하게 `thinkingConfig`가 400으로 거부되면 그 필드만 빼고 1회 재시도한다.

- 실패(타임아웃/빈 응답 등)해도 임시 제목이 그대로 유지되므로 안전 — 채팅 원문 그대로가 최종 제목으로 남는 경우는 "제목 생성이 실패했고 사용자가 그 세션을 다시 열지 않은" 드문 경우뿐이며, 다음에 목록을 새로고침(`fetchChatSessions`)하면 갱신된 제목이 보인다.
- 클라이언트는 이 갱신을 직접 트리거하지 않는다(제목은 서버가 생성한 값만 허용 — `nrm_rpc_chat_update_session_title`은 anon/authenticated에 GRANT하지 않음).
- 제목 생성에 쓴 토큰은 `LLMUserQuota`(개인 월간 누적)에는 합산하지만, `LLMTokenHistory`에는 별도 행을 만들지 않는다(제공자 일일/월간 한도 집계 기준이 `LLMTokenHistory`라 실제 채팅 호출만 남기고, 제목 생성은 소량이라 그 집계에서는 무시).

**현재 활성 LLM 모델 (2026-07-22 기준)**: 사용자 요청으로 `Type='LLM'` 중 `models/gemini-3.1-flash-lite`(`ProviderID=21`, Gemini 3.1 Flash Lite)와 `models/gemini-3.5-flash`(`ProviderID=28`, Gemini 3.5 Flash) 두 개만 `IsActive=true`로 남기고 나머지 LLM 모델은 전부 `IsActive=false`로 전환했다(`20260722150000_llm_provider_activate_gemini31_35.sql`). `Type<>'LLM'`(Embedding/TTS/Image/Video)은 이 변경과 무관하게 그대로 둔다. `admin` SerialNo는 이미 전체 `ProviderID`에 대해 `LLMUserPermission`(`IsApproved=true`, 무제한)을 갖고 있어(`scripts/seed-llm-admin-permissions-all.mjs`) 비활성화된 모델도 권한 자체는 남아있지만, `LLMProvider.IsActive=false`면 `llm-chat-send`가 `provider_unavailable`로 막는다. Google이 모델을 sunset하거나 활성 모델을 다시 바꿀 때는 이 마이그레이션 패턴(대상 `ModelName` 목록으로 `IsActive` 갱신)을 그대로 재사용하면 된다 — `llm_call_failed`(`status=404`) 로그로 감지.

### 로깅 — 서버(Edge Function) + 앱(client)

**서버(`supabase/functions/llm-chat-send/index.ts`)**: 요청마다 `requestId`(UUID)를 하나 생성해 모든 로그 줄에 붙인다. Supabase Dashboard → Edge Functions → `llm-chat-send` → Logs (또는 `supabase functions logs llm-chat-send`)에서 `requestId`로 grep하면 그 요청의 전체 흐름을 순서대로 재구성할 수 있다. 단계별 이벤트:

| event | 의미 |
| --- | --- |
| `request_received` | 파라미터 검증 통과 직후 (serialNo/providerId/sessionId/messageLength/미리보기) |
| `invalid_json` / `invalid_params` / `method_not_allowed` / `server_misconfigured` | 요청 자체 문제 |
| `prepare_turn_ok` / `prepare_turn_failed` | 1번 RPC 결과 + 소요시간(`elapsedMs`) + provider(dailyLimit/monthlyLimit/사용량 포함)/permission/quota 요약 |
| `provider_unavailable` | `LLMProvider`가 없거나 `IsActive=false` |
| `provider_daily_limit_exceeded` / `provider_monthly_limit_exceeded` | 모델 자체의 `DailyLimit`/`MonthlyLimit`(전체 사용자 합산) 소진 (AI 요청 자체를 하지 않음) |
| `permission_denied` | `LLMUserPermission` 미승인 (AI 요청 자체를 하지 않음) |
| `quota_exceeded` | 개인 `AllocatedToken` 초과 (AI 요청 자체를 하지 않음) |
| `adapter_missing` | `ProviderName`에 대응하는 어댑터 미구현 |
| `llm_call_start` / `llm_call_ok` / `llm_call_failed` | 실제 LLM API 호출 — `elapsedMs`, 토큰 수, 실패 `kind`(`auth`/`network`/`other`) + HTTP status |
| `finalize_turn_ok` / `finalize_turn_failed` | 2번 RPC 결과 |
| `quota_increment_ok` / `quota_increment_failed` / `quota_increment_threw` | 백그라운드(`waitUntil`) 쿼터 누적 결과 — 응답 반환 **후** 로그이므로 클라이언트 응답 시점보다 늦게 찍힐 수 있음(정상) |
| `title_generate_skipped` / `title_update_ok` / `title_update_failed` / `title_generate_threw` / `title_quota_increment_failed` | 백그라운드(`waitUntil`) 대화 제목 생성 결과 — 새 세션(`isNewSession`)에서만, 응답 반환 후 |
| `stream_cancelled_by_client` | 클라이언트가 스트림 읽기를 중단(앱 종료·화면 이탈 등) — `ReadableStream.cancel` |
| `stream_unhandled_error` | 스트림 `start()` 콜백 내부에서 위 어디에도 안 걸린 예외 — `error` 이벤트 전송 후 스트림 종료 |
| `request_done` | 요청 종료 요약 1줄 — `outcome`(`success`/`provider_daily_limit_exceeded`/`provider_monthly_limit_exceeded`/`permission_denied`/`quota_exceeded`/`llm_call_failed`/`provider_unavailable`/`adapter_missing`/`finalize_failed`) + `totalElapsedMs`. 세부 값은 위 단계별 로그에만 있고 여기서는 반복하지 않음(중복 방지) |
| `unhandled_error` | 위 어디에도 안 걸린 예외(스트림 시작 전) — 항상 최상위 `try/catch`로 포착되어 500으로 응답 |

ApiKey와 대화 전문은 로그에 남기지 않는다(메시지·응답은 60자 미리보기만, 길이는 전체).

**앱(`app/lib/nrmLlmChatSend.ts`, tag=`ailab.llmSend`)**: `logNrmDev`/`logNrmRunError`(`app/lib/nrmDevLog.ts`)로 `start`(요청 직전) → `ok`(성공, 서버가 돌려준 `requestId` 포함) 또는 `fetch_error`(연결 자체 실패)/`server_error`(non-2xx 응답)/`stream_error`(스트림 도중 오류)/`no_final`(스트림이 `final` 없이 끝남)을 기록한다. 서버 로그의 `requestId`와 앱 로그의 `requestId`가 같으므로, 사용자가 "채팅이 안 돼요"라고 하면 앱 로그(파일 로그 토글 on 시 릴리스 APK에도 기록됨)에서 `requestId`를 찾아 서버 로그와 대조해 정확히 어느 단계에서 실패했는지 바로 알 수 있다. `NrmDiscoverAiLabScreen.tsx`의 `ailab.send`/`ailab.messages`/`ailab.delete`/`ailab.sessions` 로그는 UI 단(어떤 대화/세션에서 발생했는지)의 컨텍스트만 추가하며, `nrmSbSelect`/`nrmSbRpc`(태그 `supabase.crud`)가 이미 찍는 원본 DB 에러와는 중복되지 않는다.

### 사용량 조회 화면 — AI Lab 좌측 메뉴 (2026-07-22)

AI Lab 좌측 메뉴의 「사용량 조회」는 모델(`LLMProvider`)별 월간 할당 토큰(`LLMUserPermission.AllocatedToken`)과 그 달 사용 토큰(`LLMUserQuota.TotalToken`)을 도넛 차트로 보여준다. 서버 RPC 없이 클라이언트가 두 테이블을 직접 SELECT한다(2026-07-21 보안 강화 마이그레이션에서 이미 anon/authenticated에 `SELECT ... USING (true)`를 허용해뒀고, `ApiKey`만 컬럼 단위로 막혀 있어 이 두 테이블은 애초에 막을 컬럼이 없다).

- **`app/lib/nrmLlmUsageClient.ts`**
  - `fetchLlmUsageProviderOptions(serialNo)` — `LLMUserPermission`에서 `SerialNo` + `IsApproved=true`인 행만 가져와 `LLMProvider`(캐시된 `fetchLlmProvidersForAiLab()`) 목록과 조인해 모델 선택 드롭다운 항목을 만든다. `LLMProvider.ApiKey`는 원래 이 목록에 없다(공개 컬럼만 select).
  - `fetchLlmUsageMonthSnapshot(serialNo, providerId, targetMonth)` — 특정 모델 × 특정월(YYYYMM)의 `LLMUserPermission`(1건, `maybeSingle`) + `LLMUserQuota`(1건, UNIQUE(`SerialNo`,`ProviderID`,`TargetMonth`)라 항상 0~1건)를 병렬 조회해 합친다. 해당 월 사용 기록이 없으면(`LLMUserQuota` 행 없음) `usedToken=0`으로 취급 — "그 달 아직 안 썼음"과 동일하므로 별도 처리가 필요 없다.
  - `isNrmLlmAllocationUnlimited(allocatedToken)` — `AllocatedToken === 0`(`NRM_LLM_UNLIMITED_ALLOCATED_TOKEN`) 여부만 판별하는 얇은 헬퍼(기존 규칙 재사용).
- **`app/lib/nrmLlmUsageMonth.ts`** — `LLMUserQuota.TargetMonth`(`YYYYMM`) 전용 월 계산(`nrmCurrentTargetMonth`/`nrmShiftTargetMonth`/`nrmIsFutureTargetMonth`/`nrmFormatTargetMonthLabel`). 미래 월로는 이동 불가(다음 달 버튼 비활성)하되, 과거로는 데이터가 없어도(당시 `LLMUserQuota` 행이 없으면 0으로 표시) 자유롭게 이동 가능.
- **`app/components/nrm/discover/NrmAiLabUsageDonut.tsx`** — `react-native-svg`의 `Circle` + `Animated.createAnimatedComponent`로 만든 순수 도넛 컴포넌트. 모델/월이 바뀔 때마다 `strokeDashoffset`을 0%에서 목표값까지 다시 애니메이션(`Animated.timing`, 900ms, ease-out)해 "스르륵" 채워지는 효과를 낸다.
- **`app/components/nrm/discover/NrmAiLabUsagePanel.tsx`** — 실제 화면(모델 선택 트리거 + 월 이동 화살표 + 도넛 + 사용/할당/남은 토큰 통계). `AllocatedToken=0`(무제한)이면 퍼센트 개념이 없으므로 도넛을 항상 100%(`success` 색)로 채우고 중앙에 인피니티 아이콘 + "무제한"을 표시, 하단 통계에서 "남은 토큰" 행은 숨긴다. 그 모델에 대해 `LLMUserPermission` 행 자체가 없거나 `IsApproved=false`면("사용 권한 없음") 도넛 대신 안내 문구만 보여준다.
- **`app/components/nrm/discover/NrmAiLabSidebar.tsx`** — 「사용량 조회」패널(`panel==='usage'`)에서 위 `NrmAiLabUsagePanel`을 렌더링. 기본 선택 모델은 AI Lab에서 현재 쓰고 있는 모델(`llmProviderId` prop, 승인 목록에 있을 때만)이고, 없으면 승인된 첫 모델로 대체한다. `serialNo`(`app/lib/nrmLlmSerialNo.ts` 규칙과 동일한 문자열)는 `NrmDiscoverAiLabScreen.tsx`가 이미 갖고 있는 값을 그대로 prop으로 내려받아 재조회하지 않는다.

## LLMUserMonthlyAllocation

관리자페이지 「AI토큰 할당」의 월별(YYYYMM) 설정 이력. **실시간 사용 한도 체크에는 관여하지 않는다** — 그 역할은 여전히 `LLMUserPermission.AllocatedToken`(항상 "현재 적용 중인 값")이 담당한다. 이 테이블은 "그 값이 언제·얼마로 설정됐는지" 조회용 이력일 뿐이다.

| 컬럼 | 타입 | 기본값 | NULL | 설명 |
|------|------|--------|------|------|
| `AllocationID` | `bigint` IDENTITY | — | NO | 할당 이력 고유번호 **(복합 PK)** |
| `SerialNo` | `varchar` | — | NO | 사용자 일련번호 **(복합 PK)** |
| `ProviderID` | `bigint` | — | NO | LLM 제공자 고유번호 |
| `TargetMonth` | `varchar(6)` | — | NO | 할당 대상월 (`YYYYMM`) |
| `AllocatedToken` | `bigint` | `0` | NO | 해당 월에 설정된 할당 토큰 (`0` = 무제한) |
| `UpdatedBySerialNo` | `varchar` | — | YES | 설정을 실행한 관리자 SerialNo (항상 `admin`, 감사용) |
| `RegDate` | `timestamptz` | `now()` | NO | 최초 생성일시 |
| `UpdateDate` | `timestamptz` | `now()` | NO | 최종 수정일시 |

- **PK** `PK_LLMUserMonthlyAllocation` (`AllocationID`, `SerialNo`)
- **UNIQUE** `UX_LLMUserMonthlyAllocation` (`SerialNo`, `ProviderID`, `TargetMonth`) → 동일 사용자·제공자·월은 1건만 존재(그 달의 마지막 설정값만 보관, 수정 이력 자체는 남기지 않음).
- RLS: `SELECT`만 anon/authenticated 허용(`USING (true)`), 쓰기는 아래 RPC 전용.

### 관리자 RPC — `nrm_rpc_admin_set_llm_user_token_allocation`

`supabase/migrations/20260722140000_llm_user_monthly_allocation.sql`. 파라미터: `p_caller_serial`(admin 검증용), `p_serial_no`, `p_provider_id`, `p_target_month`(YYYYMM), `p_allocated_token`, `p_is_approved`. 한 트랜잭션에서:

1. `LLMUserPermission`(`SerialNo`,`ProviderID`) upsert — `IsApproved`/`AllocatedToken`/`ApprovedDate`/`UpdateDate` 갱신(**실시간 적용값**).
2. `LLMUserMonthlyAllocation`(`SerialNo`,`ProviderID`,`TargetMonth`) upsert — 그 달 설정값 이력 기록.

`nrm_is_admin_caller`로 `p_caller_serial === 'admin'`이 아니면 `admin required` 예외. `anon`/`authenticated`에 `GRANT EXECUTE`(APK publishable key로 호출, 관리자 세션 게이트는 앱 UI 단 `nrmAdminAuth`가 담당 — `구현 시 참고` 항목 참고).

## 구현 시 참고

- 호출 전: `LLMUserPermission`에서 `IsApproved`·`AllocatedToken`을 확인한다.
- **`AllocatedToken = 0`** → 할당 한도 없음(무제한). (`LLMProvider`.`DailyLimit`/`MonthlyLimit`의 `0`과 동일 규칙)
- `SerialNo`(`LLMUserQuota`/`LLMTokenHistory`/`LLMUserPermission`)는 **varchar** — 앱 `getNrmAppSerialNo()` 원문을 형 변환 없이 그대로 저장한다. 앱: `app/lib/nrmLlmSerialNo.ts`
  - **admin APK**: text `"admin"` 그대로 저장 (과거엔 `bigint`여서 `0`으로 매핑했었으나 varchar 전환 후 더 이상 변환하지 않음)
  - **커스텀 APK**: numeric serial도 문자열 그대로 저장 (앞자리 `0` 보존, 예: `"01092452918"`)
- 호출 후: `LLMTokenHistory` INSERT + 해당 월 `LLMUserQuota` upsert(누적)를 함께 갱신하는 흐름을 권장.
- **복합 PK**: `LLMUserPermission` (`PermissionID`, `SerialNo`), `LLMUserQuota` (`QuotaID`, `SerialNo`), `LLMTokenHistory` (`HistoryID`, `SerialNo`). PostgREST upsert·앱 코드에서 `onConflict` 대상 컬럼을 복합 PK에 맞출 것.
- `DailyLimit` / `MonthlyLimit`는 **제공자** 단위 제한, `AllocatedToken`은 **사용자×제공자** 할당 한도다.
- 대화 세션·메시지는 [`chat.md`](./chat.md) (`ChatSession`, `ChatMessage`).
- FK(`ProviderID` → `LLMProvider`)는 현재 DDL에 없음. 필요 시 마이그레이션으로 추가 가능.
- 대화 제목은 `nrm_rpc_chat_update_session_title`(service_role 전용)로만 갱신된다 — 위 "대화 제목 자동 생성" 참고.
