# LLM 관련 테이블

원격 Supabase에 이미 생성된 스키마다. (PascalCase 식별자, quoted `"TableName"`)

관계 개요:

```
LLMProvider (1) ──< LLMUserPermission (N)  사용자×제공자 승인·할당 토큰
                ├──< LLMUserQuota (N)      사용자×제공자×월 누적
                ├──< LLMTokenHistory (N)   호출 단위 이력
                └──< ChatSession (N)       대화 세션 → ChatMessage (N)
                                           (상세: chat.md)
```

`SerialNo`는 사용자 일련번호다. `LLMUserQuota`·`LLMTokenHistory`·`LLMUserPermission`의 `SerialNo`는 **varchar**로, 기존 `nrm_user_list.serial_no`(**text**)·앱 `getNrmAppSerialNo()` 값(예: `"admin"`, 숫자 문자열)을 형 변환 없이 원문 그대로 저장한다. (과거 `bigint`였던 것을 `varchar`로 변경)

## LLMProvider

## 보안 — RLS·컬럼 권한 (`20260721120000_llm_chat_security_harden.sql`)

이 6개 테이블은 생성 시 RLS를 켜지 않아 "쓰기는 RPC로만"이라는 원칙이 적용되지 않고 있었다. 아래로 강화:

- `LLMProvider`/`LLMUserPermission`/`LLMUserQuota`/`LLMTokenHistory`/`ChatSession`/`ChatMessage` 모두 `ENABLE ROW LEVEL SECURITY` + `SELECT` 정책만 anon/authenticated에 허용(`USING (true)`). **쓰기 정책은 없음** → 모든 쓰기는 `nrm_rpc_*` (SECURITY DEFINER) 경유.
- `LLMProvider."ApiKey"`는 RLS(row 단위)로 못 숨기므로 **컬럼 단위**로 `REVOKE SELECT ... FROM anon, authenticated` 후 나머지 컬럼만 `GRANT SELECT (...)`. 앱이 실수로 `select=*`를 하더라도 DB가 `ApiKey`를 막는다.

## AI Lab 채팅 전송 — Edge Function + RPC (실제 구현)

`ApiKey`는 클라이언트(APK)에 절대 내려주지 않는다. 실제 LLM 호출은 Edge Function
`supabase/functions/llm-chat-send`(service_role)에서만 수행:

1. **`nrm_rpc_chat_prepare_turn`** (service_role 전용, `20260721130000_chat_send_rpc.sql` → 한도 체크 필드 추가는 `20260721140000_chat_provider_limit_check.sql`) — DB 왕복 1회로:
   세션 확보/생성 → 사용자 메시지 저장 → `LLMProvider`(ApiKey 포함, `DailyLimit`/`MonthlyLimit`과 그 기준 **전체 사용자 합산** 현재 사용량 `providerDailyUsed`/`providerMonthlyUsed`도 함께)·`LLMUserPermission`·해당월 `LLMUserQuota`·최근 대화이력(최대 40건, `system` 제외)을 한 번에 조회해 반환.
   - `providerDailyUsed` = 오늘(UTC) `LLMTokenHistory."TotalToken"` 합계(해당 `ProviderID`, 전체 사용자). `DailyLimit=0`이면 이 집계 자체를 건너뛴다(가장 흔한 "무제한" 케이스에서 추가 비용 없음).
   - `providerMonthlyUsed` = 이번 달 `LLMUserQuota."TotalToken"` 합계(해당 `ProviderID`, 전체 사용자). `MonthlyLimit=0`이면 건너뛴다.
2. Edge Function이 위 결과로 **① 제공자(모델) 단위 `DailyLimit`/`MonthlyLimit`** → **② 사용자 권한(`IsApproved`)** → **③ 사용자 개인 쿼터(`AllocatedToken`)** 순으로 선체크 후, 모두 통과하면 프로바이더 어댑터(`ProviderName` 기준, 지금은 `Gemini`만 구현)로 실제 LLM API를 호출. Gemini `generateContent` 응답의 `usageMetadata`(`promptTokenCount`/`candidatesTokenCount`/`totalTokenCount`)를 그대로 써서 **토큰 집계용 별도 API 호출이 필요 없다.**
3. **`nrm_rpc_chat_finalize_turn`** (service_role 전용) — DB 왕복 1회로: 응답(`assistant`/`system`) 메시지 저장 + `ChatSession.UpdateDate` 갱신 + (실제로 AI 요청을 시도한 경우만) `LLMTokenHistory` 기록.
4. **`nrm_rpc_increment_llm_user_quota`** (service_role 전용) — `LLMUserQuota` 누적 upsert(`ON CONFLICT` 원자적 증가). 사용자 응답을 이미 반환한 **뒤** `EdgeRuntime.waitUntil()`로 백그라운드 실행 — 응답 지연에 전혀 영향 없음.

사전 체크 실패(제공자 한도 소진/권한 없음/쿼터 초과)는 AI 요청 자체를 하지 않으므로 `LLMTokenHistory`에 기록하지 않는다(요구사항). 네트워크 오류·프로바이더 오류처럼 **AI 요청을 시도한** 경우는 실패해도 `isSucess=false`로 기록한다.

**"토큰이 만료되었을 경우" 메시지의 의미 구분** (설계 결정, 2026-07-21):
- 개인 할당량(`LLMUserPermission.AllocatedToken`) 소진 → `토큰이 만료되었어요. 관리자에게 문의해주세요.` (관리자가 늘려주면 바로 해결됨)
- 모델(`LLMProvider`) 자체의 `DailyLimit`/`MonthlyLimit`(전체 사용자 합산) 소진 → `지금 이 모델을 많은 사용자가 이용하고 있어 잠시 이용이 어려워요. 나중에 다시 시도해 주세요.` (관리자 문의로 즉시 해결되는 성격이 아니므로 문구를 구분)
- Gemini API 자체의 인증 오류(401/403) → `네트워크 문제로 요청할 수 없어요...` (앱에 실사용자 로그인 토큰이 없어 "토큰"이라는 표현은 위 두 가지 앱 내부 토큰 할당량 개념에만 사용)

멀티 프로바이더 확장: Edge Function 안 `ADAPTERS: Record<ProviderName, LlmAdapter>` 맵에 새 어댑터(예: OpenAI)를 추가하고 `LLMProvider.ProviderName`을 맞추면 나머지 로직(권한/쿼터/기록/세션)은 그대로 재사용된다.

**현재 활성 LLM 모델 (2026-07-21 기준)**: `models/gemini-2.5-flash`(`ProviderID=1`)는 Google이 신규 호출을 차단(`generateContent` 404 "no longer available to new users")해 `IsActive=false`로 변경했다(이력 보존용으로 행은 남김). 대체로 `models/gemini-flash-latest`(`ProviderID=11`, 2026-07-21 기준 `gemini-3.5-flash`로 alias)를 `IsActive=true`로 켜고 `LLMUserPermission`에 admin 무제한 권한을 추가했다. `models/gemini-embedding-2`(`ProviderID=42`, `Type=Embedding`)는 변경 없음. Google이 모델을 sunset할 때마다 같은 방식(기존 행 `IsActive=false` + 대체 모델 행 `IsActive=true`)으로 대응한다 — `llm-chat-send` 로그의 `llm_call_failed`(`status=404`) 이벤트로 즉시 감지 가능.

### 로깅 — 서버(Edge Function) + 앱(client)

**서버(`supabase/functions/llm-chat-send/index.ts`)**: 요청마다 `requestId`(UUID)를 하나 생성해 모든 로그 줄에 붙인다. Supabase Dashboard → Edge Functions → `llm-chat-send` → Logs (또는 `supabase functions logs llm-chat-send`)에서 `requestId`로 grep하면 그 요청의 전체 흐름을 순서대로 재구성할 수 있다. 단계별 이벤트:

| event | 의미 |
| --- | --- |
| `request_received` | 파라미터 검증 통과 직후 (serialNo/providerId/sessionId/messageLength/미리보기) |
| `invalid_json` / `invalid_params` / `method_not_allowed` / `server_misconfigured` | 요청 자체 문제 |
| `prepare_turn_ok` / `prepare_turn_failed` | 1번 RPC 결과 + 소요시간(`elapsedMs`) + provider(dailyLimit/monthlyLimit/사용량 포함)/permission/quota 요약 |
| `provider_unavailable` | `LLMProvider`가 없거나 `IsActive=false` |
| `provider_daily_limit_exceeded` / `provider_monthly_limit_exceeded` | 모델 자체의 `DailyLimit`/`MonthlyLimit`(전체 사용자 합산) 소진 (AI 요청 자체를 하지 않음) |
| `permission_denied` | `LLMUserPermission` 미승인 (AI 요청 자체를 하지 않음) |
| `quota_exceeded` | 개인 `AllocatedToken` 초과 (AI 요청 자체를 하지 않음) |
| `adapter_missing` | `ProviderName`에 대응하는 어댑터 미구현 |
| `llm_call_start` / `llm_call_ok` / `llm_call_failed` | 실제 LLM API 호출 — `elapsedMs`, 토큰 수, 실패 `kind`(`auth`/`network`/`other`) + HTTP status |
| `finalize_turn_ok` / `finalize_turn_failed` | 2번 RPC 결과 |
| `quota_increment_ok` / `quota_increment_failed` / `quota_increment_threw` | 백그라운드(`waitUntil`) 쿼터 누적 결과 — 응답 반환 **후** 로그이므로 클라이언트 응답 시점보다 늦게 찍힐 수 있음(정상) |
| `request_done` | 요청 종료 요약 1줄 — `outcome`(`success`/`provider_daily_limit_exceeded`/`provider_monthly_limit_exceeded`/`permission_denied`/`quota_exceeded`/`llm_call_failed`/`provider_unavailable`/`adapter_missing`/`finalize_failed`) + `totalElapsedMs`. 세부 값은 위 단계별 로그에만 있고 여기서는 반복하지 않음(중복 방지) |
| `unhandled_error` | 위 어디에도 안 걸린 예외 — 항상 최상위 `try/catch`로 포착되어 500으로 응답 |

ApiKey와 대화 전문은 로그에 남기지 않는다(메시지·응답은 60자 미리보기만, 길이는 전체).

**앱(`app/lib/nrmLlmChatSend.ts`, tag=`ailab.llmSend`)**: `logNrmDev`/`logNrmRunError`(`app/lib/nrmDevLog.ts`)로 `start`(요청 직전) → `ok`(성공, 서버가 돌려준 `requestId` 포함) 또는 `invoke_error`/`server_error`(실패)를 기록한다. 서버 로그의 `requestId`와 앱 로그의 `requestId`가 같으므로, 사용자가 "채팅이 안 돼요"라고 하면 앱 로그(파일 로그 토글 on 시 릴리스 APK에도 기록됨)에서 `requestId`를 찾아 서버 로그와 대조해 정확히 어느 단계에서 실패했는지 바로 알 수 있다. `NrmDiscoverAiLabScreen.tsx`의 `ailab.send`/`ailab.messages`/`ailab.delete`/`ailab.sessions` 로그는 UI 단(어떤 대화/세션에서 발생했는지)의 컨텍스트만 추가하며, `nrmSbSelect`/`nrmSbRpc`(태그 `supabase.crud`)가 이미 찍는 원본 DB 에러와는 중복되지 않는다.

## 구현 시 참고

- 호출 전: `LLMUserPermission`에서 `IsApproved`·`AllocatedToken`을 확인한다.
- **`AllocatedToken = 0`** → 할당 한도 없음(무제한). (`LLMProvider`.`DailyLimit`/`MonthlyLimit`의 `0`과 동일 규칙)
- `SerialNo`(`LLMUserQuota`/`LLMTokenHistory`/`LLMUserPermission`)는 **varchar** — 앱 `getNrmAppSerialNo()` 원문을 형 변환 없이 그대로 저장한다. 앱: `app/lib/nrmLlmSerialNo.ts`
  - **admin APK**: text `"admin"` 그대로 저장 (과거엔 `bigint`여서 `0`으로 매핑했었으나 varchar 전환 후 더 이상 변환하지 않음)
  - **커스텀 APK**: numeric serial도 문자열 그대로 저장 (앞자리 `0` 보존, 예: `"01092452918"`)
- 호출 후: `LLMTokenHistory` INSERT + 해당 월 `LLMUserQuota` upsert(누적)를 함께 갱신하는 흐름을 권장.
- **복합 PK**: `LLMUserPermission` (`PermissionID`, `SerialNo`), `LLMUserQuota` (`QuotaID`, `SerialNo`), `LLMTokenHistory` (`HistoryID`, `SerialNo`). PostgREST upsert·앱 코드에서 `onConflict` 대상 컬럼을 복합 PK에 맞출 것.
- `DailyLimit` / `MonthlyLimit`는 **제공자** 단위 제한, `AllocatedToken`은 **사용자×제공자** 할당 한도다.
- 대화 세션·메시지는 [`chat.md`](./chat.md) (`ChatSession`, `ChatMessage`).
- FK(`ProviderID` → `LLMProvider`)는 현재 DDL에 없음. 필요 시 마이그레이션으로 추가 가능.
